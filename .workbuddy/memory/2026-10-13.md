## 图片显示问题根因（已定位并验证修复方案）
- 排查排除：文件缺失、文件损坏、文件名异常字符、404 —— 均无问题，121/121 资源可正常解码。
- **真正根因**：`symbol-*.png` 是 RGB 模式、纯白背景、无 Alpha 通道，但 CSS 统一套了`mix-blend-mode:multiply`。multiply 原意是配合透明底 PNG，白底 RGB 遇上它会导致浅底几乎隐形、深底出现白色方块。
- 该 bug 在 Windows 开发机不明显，是因为 multiply 表现完全依赖底层背景色。
- 修复方案 A（推荐，已出对比图验证可行）：白底转 Alpha，边缘按亮度衰减保留原色避免发黑。验证图见 `docs/图片问题-修复对比.png`（左原图 / 右修复后）。
- 注意 `ritual-stone-transparent.png` 本身已是 RGBA 真透明，无需处理。

`ADMIN.page(rest)` 与守卫的 saveRedirect 都改用 `rest`。

### 需求2：数据来源核查结论（重要，写给未来的自己）
**journal 页 5 个模块的数据来源并不统一：**

| 模块 | 数据来源 | 状态 |
|---|---|---|
| 最近心情 | `records` →数据库 moments | ✅ 已入库 |
| 我收藏的字 | `favorites` → 数据库 favorites | ✅ 已入库 |
| 留给自己的片刻 | `records` → 数据库 moments | ✅ 已入库 |

| 我的账号 | 跳转到 `#account` | ✅ 数据库 users |

## 核查：moments 的显示与覆盖规则（用户提问，回答备查）
### 结论：每天一条，**同一天重复保存是覆盖而非追加**；两个区块显示范围不同

**存储层（一天一条）**
- DB：`moments` 表有 `UNIQUE(user_id, date)`；`PUT /api/moments` 是
  "按 (user_id, date) 查→有则 UPDATE，无则 INSERT"，所以**同一天永远只有一条**。
- 前端：`records` 用 `new Map(...)` 以 date 为键去重；保存时
  `findIndex(x=>x.date===r.date)` 命中则 `records[i]=r` 覆盖，否则 push。
- **实测**：10-13 先存 symbol=26/note=第二天，再存 symbol=51/note=第二天改过 →
  数据库该日只剩 symbol=51/note=第二天改过；10-12、10-14 各自独立保留，共 3 条。
- 所以：**不会丢历史，但同一天内先抽的会被后抽的覆盖**（当天多次抽字只留最后一次保存）。

**显示层（两个区块范围不同）**
- 「最近心情」= `sorted.slice(0,7).reverse()`
  → 只取**最近 7 天**，且 `.reverse()` 使其**按日期升序**（最早在左、最新在右）。
  实测 10 天数据 → 显示 7 条，日期 10/4→10/10 递增。
- 「留给自己的片刻」= `sorted.map(...)`（无 slice）
  → **显示全部记录**，日期降序（最新在上）。
- 顶部统计 `records.length` = 累计天数，不是 7。

**为什么这样设计**：7 条正好对应「每天 7 次体验配额」，是刻意的时间窗口，不是 bug。

## moments 改为「一天多条」+ UTC 精确时间戳
### 起因
用户反馈「留给自己的片刻并未显示全部记录，今天的最新覆盖了今天之前的记录」。

### 先澄清一个事实（回答用户的疑问）
**同一天内会互相覆盖，但不会覆盖前一天。** 实测：10-12 存 2 次、10-13 存 3 次 → 旧逻辑下只剩 2 条
（10-12 的第 1 次、10-13 的第 3 次）。所以用户看到的是「当天覆盖」，不是「今天吃掉昨天」。

### 改动：一天可留多条
**数据库**
- `moments` 去掉 `UNIQUE(user_id, date)`，改为索引 `ix_moment_user_created (user_id, created_at)`
- SQLite 已存在的旧表需**重建**（唯一约束不能 ALTER 掉）：
  `CREATE TABLE moments_new ... INSERT SELECT ... DROP ... RENAME` + 补建索引
- ⚠️ 线上 PostgreSQL 也必须执行对应迁移（ALTER TABLE DROP CONSTRAINT + CREATE INDEX），
  已在部署文档标注需补 Alembic 迁移脚本

**API**
- `MomentIn` 增加可选 `id`：带 id = 编辑该条，不带 = **新增一条**
- `MomentOut` 增加 `id` 与 `created_at`
- 列表排序改为 `created_at DESC, id DESC`（原来是 `date DESC`）
- `DELETE /api/moments/{moment_id}` —— 参数从日期改为 id（一天多条后不能再按日期删）
- 迁移接口的幂等判重从「日期」改为「日期+字+备注」组合，避免重复导入产生副本

**前端**
- `records` 去重键从 `r.date` 改为 `r.id`（无 id 时退回 date+symbol+note组合）
- 保存时不再 `findIndex` 替换，改为 push 新增
- `#saved/{param}` 路由改为**按记录 id 定位**（param 为纯数字时优先当 id 匹配），旧日期链接仍兼容
- `data-route="saved/..."` 两处改用 id
- 新增 `fStamp(r)`：`M月D日 HH:mm:ss (UTC)`，取 UTC 各分量而非本地时区

### 踩坑：SQLite 时区丢失导致时刻偏移 8 小时
`fStamp` 初版用 `new Date('2026-10-13T12:55:03')`（无 Z）→ JS 按**本地时区**解读 → 显示 04:55:03（差 8 小时）。
**修法**：正则判断是否带时区标记，无则补 `'Z'`：
```js
const zoned=/[Zz]|[+-]\d{2}:?\d{2}$/.test(iso) ? iso : iso+'Z';
```
SQLite 的 DATETIME 不存时区，Python 返回的是 UTC 值但不带 Z；PostgreSQL 的
`timestamptz` 会带 `+00:00`，该正则同样兼容。

### 显示范围调整
- 「最近心情」：`sorted.slice(0,7)` → `sorted.slice()`，**去掉 7 条上限，显示全部**，保持日期升序
- 「留给自己的片刻」：本来就是全量，只需换时间格式

### 实测
- 10-12 存 2 次 + 10-13 存 3 次 → 数据库 5 条全保留（id 2~6）
- 带 id 编辑其中一条 → 总数仍 5，被编辑那条备注已更新
- 5 条记录 → 两个区块都显示 5 条，时间标签如「10月13日 12:55:03 (UTC)」
- 未登录访问 moments 仍 401；编辑不存在的 id 返回 404
- 缓存标识 `?v=20261013-multimoment`
